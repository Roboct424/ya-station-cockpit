# Дневник разработки

Здесь фиксируются решения, ошибки и их причины — чтобы через месяц не гадать,
почему сделано именно так. Формат: дата, что сделано, что сломалось, как починили.

---

## 2026-11-18 · Фаза 0: фундамент

### Задача

Начать новый проект на Rust: приложение для локальной настройки и обслуживания
Яндекс Станций (мастер + консоль), с журналом каждого шага, проверками и откатом.
Пока без сети и перехвата — только скелет, который не стыдно развивать.

### Принятые решения

1. **Workspace из четырёх крейтов** (`core`, `config`, `doctor`, `cli`).
   Причина: ядро не должно зависеть от CLI и от платформы; позже появится
   `api` (локальный HTTP) и `app` (Tauri), и они подключатся к тому же ядру.

2. **Журнал — JSON Lines, а не SQLite.**
   Причины: нет нативной зависимости; каждая строка сбрасывается на диск, поэтому
   падение процесса не теряет историю; файл читается `grep`/`jq` без нашего кода.
   Когда понадобятся индексы и запросы — подменим реализацию `Journal`,
   не меняя вызывающий код. Трейт уже отделён.

3. **Шаг = транзакция.** Контракт `Step`:
   `is_done` (предусловие) → `run` (действие) → `verify` (доказательство) →
   `rollback` (компенсация). Это ядро «банковского» поведения: нельзя «сделать
   и надеяться».

4. **Упавший шаг не откатывается.** Откатываются только успешно завершённые
   шаги, в обратном порядке. Упавший шаг либо не изменил состояние, либо
   оставил его частично — для таких случаев позже добавим `recover`.
   Это зафиксировано тестом `runner_rolls_back_only_executed_steps`,
   чтобы не «починить» случайно.

5. **Ошибка = код + подсказка.** `CockpitError::code()` и `hint()` дают UI и
   журналу машиночитаемый код (`run.step_failed`) и человеческое «что делать».
   Позже к этому добавится таблица «код → причина → лечение» в `doctor`.

6. **Конфиг валидируется целиком.** `Config::validate()` возвращает список
   проблем, а не первую. Причина: пользователю нужно видеть все ошибки сразу.

### Что реализовано

- `cockpit-core`: `Record` (события), `JsonlJournal`, `Step`, `Runner`,
  `CockpitError`, `Context`.
- `cockpit-config`: TOML-конфиг с умолчаниями, `deny_unknown_fields`
  (опечатка в ключе = ошибка, а не тихий игнор), валидация, шаблон `cockpit.toml`.
- `cockpit-doctor`: 8 проб (платформа, права, конфиг, каталог, журнал, DNS-порт,
  HTTP-порты, поддержка перехвата) с подсказками.
- `cockpit-cli`: `doctor`, `config init|check|show`, `journal tail|stats`,
  `run selfcheck`, `version`.
- Тесты: 4 на движок (журнал, успех, откат, dry-run) + 7 на конфиг.

### Ошибки и как чинили

| Что | Причина | Решение |
|---|---|---|
| `clippy: should_implement_trait` на `Runner::add` | имя `add` намекает на `std::ops::Add` | переименовали в `with_step` / `with_steps` |
| `clippy: derivable_impls` для `Config` | ручной `Default`, хотя все поля дефолтные | `#[derive(Default)]`, ручные `Default` остались у секций |
| тест ссылался на несуществующий вариант `Record::StartStepMarker` | писал тест «по памяти» | тест переписан на подсчёт `kind()` |
| первая версия теста отката проверяла не тот шаг | семантика: упавший шаг не откатывается | тест проверяет флаг **первого** шага и отсутствие отката у упавшего |

### Известные шероховатости (осознанно отложены)

1. **`doctor` создаёт `data/`** — проба записи. Формально диагностика «меняет»
   систему. Позже: проверять запись во временном каталоге, а `data/` не трогать.
2. **`Context` не содержит конфиг** — шагам он пока не нужен; появится вместе
   с сетевыми шагами, чтобы не тащить зависимость ядра на `cockpit-config`.
3. **Нет отмены по Ctrl+C** — журнал уже append-only, добавим обработчик сигнала
   и статус `run.cancelled`.
4. **Нет `recover` для частично применённых шагов** — появится, когда будут
   реальные действия (файлы, правила firewall), а не маркер.

### Следующие шаги (фаза 1)

- Трейт `NetAdapter` + две реализации-заглушки (Windows/Linux) без реальных
  вызовов, но с типами и ошибками.
- Сценарии: YAML-схема (`id`, `title`, `when`, `run`, `verify`, `rollback`),
  загрузчик и валидатор; `cockpit run <file.yaml>`.
- Горячая перезагрузка конфига (`notify` + `arc-swap`), без перезапуска.
- `doctor`: проверка занятости 53/80/443 на конкретном интерфейсе,
  определение `systemd-resolved` (Linux) и WinDivert (Windows) по путям.

## 2026-11-18 · Журнал болячек и две правки по его итогам

### Задача

Завести отдельный журнал особенностей библиотек (`docs/GOTCHAS.md`) и проверить
типовые места, где они кусают: «пусто / битые данные / повторный вызов».

### Что проверили и что нашли

| Проверка | Результат |
|---|---|
| `cockpit config show` при `Option = None` | работает (TOML опускает ключ) → G-004 |
| `cockpit doctor --json` | работает |
| явный `--config` с опечаткой | **молча игнорировался** → G-001 |
| журнал с оборванной строкой | **падал целиком** → G-002 |
| два запуска в одну мс | `run_id` мог совпасть → G-005 |

### Что исправили

1. **G-001**: `--config` стал `Option<PathBuf>`; явно указанный путь обязан
   существовать, иначе ошибка `cfg.invalid` с подсказкой. Иначе опечатка
   незаметно подменялась умолчаниями.
2. **G-002**: `Journal::read_all` теперь возвращает `JournalRead { records, skipped }`.
   Битая строка попадает в `skipped` и печатается предупреждением, история
   остаётся доступной. Добавлен тест `corrupt_line_does_not_hide_history`.
3. **G-005**: `run_id = millis-micros-seq` с атомарным счётчиком.

### Почему так, а не иначе

* Ошибку в `--config` нельзя «починить подстановкой умолчаний»: пользователь
  должен узнать, что файла нет. Это важнее, чем «удобство».
* Пропуск битых строк в журнале — компромисс: мы теряем одну запись, но не
  теряем всю историю. Для аудита это правильнее, чем «всё или ничего».
* `run_id` не должен зависеть от точности часов: счётчик — единственная
  гарантия уникальности в рамках процесса.

## 2026-11-18 · Фаза 2: таймауты, системные команды, DNS-перехват

### Что сделано

1. **Таймаут шага стал реальным.** `Step::timeout_ms` + `Runner::execute`:
   шаг выполняется в отдельном потоке, ожидание ограничено, по истечении
   возвращается `run.timeout`. Тест проверяет, что возврат происходит быстрее
   самого шага (50 мс против 300 мс).
2. **Слой системных команд** (`cockpit-net::sys`): `CommandSpec` → `CommandRunner`.
   Две реализации: `SystemRunner` (реальный запуск) и `DryRunRunner`
   (записывает команды, ничего не делает). Ошибки ОС → `NetError`.
3. **Адаптеры платформ** строят команды:
   * Windows: `netsh interface ipv4 set dnsservers`, `netsh interface portproxy`;
   * Linux: `resolvectl dns`, `iptables -t nat REDIRECT` + обратное `-D`.
   Каждое правило помнит свою команду удаления (`remove_rule`).
   Хотспот остаётся `NotImplemented` (WinRT/hostapd).
4. **DNS-перехватчик** (`cockpit-intercept`): свой минимальный парсер,
   A → заданный IPv4, AAAA → пустой ответ, мусор игнорируется.
   Команда `cockpit dns --bind … --answer … --seconds N`.

## 2026-11-18 · Фаза 3: TLS-подмена и хотспот

### Что сделано

1. **Свой CA и TLS-перехват** (`cockpit-intercept::tls`):
   * `CertAuthority::generate()` — корневой CA (rcgen);
   * `config_for(host)` — листовой сертификат по SNI с кэшем;
   * `parse_sni` — собственный разбор ClientHello (без библиотек);
   * `TlsInterceptor` — принимает соединение, подглядывает SNI через `peek`

2. **Хотспот**:
   * Windows — `netsh wlan set/start hostednetwork` (2 команды + stop);
   * Linux — генерация `hostapd.conf` и `dnsmasq.conf` в рабочем каталоге,
     запуск `hostapd -B` и `dnsmasq --conf-file`.
3. **CLI**: `cockpit tls --bind … --ca-out …` — поднимает перехватчик и
   сохраняет CA; `doctor` показывает, создан ли CA.

## 2026-11-18 · Фаза 4: настоящий TLS-прокси (туннель к апстриму)

### Что сделано

`TlsInterceptor` научился форвардить: после рукопожатия с клиентом он
открывает TLS-соединение к настоящему серверу (`host:443` по SNI, корни —
webpki-roots) и перекачивает байты в обе стороны.

Ключевые детали:
* `ForwardOptions` — порт апстрима, набор корневых сертификатов, подмена
  разрешения имени (для тестов);
* `pump` — цикл на non-blocking сокетах: оба направления обслуживаются по
  очереди, иначе взаимная блокировка (G-020);
* `--forward` в `cockpit tls` включает режим туннеля, иначе остаётся заглушка.

### Проверка (реальный интернет)

```
$ cockpit tls --bind 127.0.0.1:18443 --ca-out data\ca.pem --forward --seconds 15
TLS слушает 127.0.0.1:18443 (сертификат по SNI, туннель к реальному серверу)

$ curl --ssl-no-revoke --cacert data\ca.pem \
       --resolve example.com:18443:127.0.0.1 https://example.com:18443/
http=200 size=577
<title>Example Domain</title>
```

То есть клиент проверил наш сертификат, прокси сходил в настоящий
`example.com`, и вернулся реальный HTML.

### Тесты

Добавлены:
* `forwarding_tunnels_to_upstream` — локальный TLS-апстрим, ответ доходит;
* `forwarding_rejects_untrusted_upstream` — апстрим с чужим CA не принимается.

Всего 39 тестов. `clippy -D warnings` — чисто.

### Ограничения фазы

1. Одно соединение за раз (без пула потоков) — для отладки достаточно, для
   реальной нагрузки понадобится пул.
2. Нет HTTP/2-специфики: туннель прозрачный, поэтому h2 проходит, но
   анализировать его мы пока не умеем.
3. Для подмены на устройстве нужно установить наш CA в доверенные — это

## 2026-11-18 · Фаза 5: OTA и сбор метаданных

* `cockpit-ota`: манифест → проверка версии → загрузка с CRC32/SHA-256 →
  провенанс (URL, размер, хеши, updateId, время). Команды `ota check/fetch/list`.
* `cockpit-capture`: журнал метаданных обмена (без тел), обрезка query,
  сводка по хостам. По умолчанию выключен.
* Проверено на реальном манифесте: `ota check` корректно показывает .46 как
  обновление для .40.
* Тестов: 46. clippy/fmt — чисто.

Почему обновляли колонку: `.46` — рабочая точка для сетевого ADB через
`get_sync_info`; `.50` ломает цепочку сертификатов. OTA теперь оформлен как
отдельный шаг с проверкой и провенансом.

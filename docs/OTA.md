# OTA: проверка и загрузка прошивок

## Откуда данные

Колонка сама спрашивает облако (`/check_updates`). Ответ содержит:

| Поле | Смысл |
|---|---|
| `hasUpdate` | есть ли обновление |
| `version` | версия сборки, например `0.369.1.46.4778262943.20261013.299` |
| `critical` | критичность |
| `downloadUrl` / `fallbackUrl` | CDN, ссылка персональная (`user/<uuid>`) и может истечь |
| `crc32` | контрольная сумма архива |
| `updateId` | идентификатор обновления |

Снимок такого ответа лежит в `data/manifests.json` (по платформам).

## Команды

```bash
cockpit ota check --manifest data/manifests.json \
  --platform yandexmini_2 --current 0.369.1.40.1.20250101.1
cockpit ota fetch --manifest data/manifests.json \
  --platform yandexmini_2 --version 0.369.1.46.4778262943.20261013.299
cockpit ota list
```

`fetch` проверяет CRC32, сохраняет архив и рядом — провенанс:
откуда скачано, размер, SHA-256, `updateId`, время.

## Почему обновление — осознанный шаг

Прошивка может **закрыть** использованный путь доступа. Пример из практики:
`.46` нужна была для сетевого ADB через `get_sync_info`, а `.50` отвергает
цепочку сертификатов, которой ходят другие проекты. Поэтому:

1. сначала бэкап и проверка CRC;
2. применение — отдельным сценарием с проверкой версии после;
3. при провале — откат.

## Другие модели

Механизм общий (Quasar): отличаются `platform` и файлы
(`yandexmini_2`, `yandexmidi`, `yandexmax`, `saturn`, `plum`…).
